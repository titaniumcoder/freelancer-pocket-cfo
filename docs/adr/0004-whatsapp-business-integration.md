# ADR-0004: WhatsApp Business integration — Meta Cloud API direct, own thin client

- **Status:** Accepted
- **Date:** 2026-10-21
- **Deciders:** Rico Metzger (founder)
- **Related:** ADR-0001 (stack: Oban for idempotent ingestion), ADR-0005 (chatbot),
  ADR-0007 (support shares the channel)

## Context

WhatsApp is the product's main channel: registration, daily interaction, the chatbot,
and support all run through it. The founder's verdict: **direct Meta Cloud API — "not
even a decision"**; a BSP middleman (Twilio, 360dialog) only enters the picture if
number provisioning ever hits a wall.

The founder additionally wants the client layer **generated by us** (from Meta's own
machine-readable spec), **tested against the live API via a Livebook**, and is open to
maintaining our own library if the ecosystem's clients disappoint.

## Decision

**Integrate the WhatsApp Business Platform Cloud API directly, over a thin in-repo
client generated from Meta's published API spec. Webhook ingestion, idempotency, and
message dispatch are first-class Phoenix/Oban machinery.**

The API quality justifies this: Meta publishes the Cloud API with a complete OpenAPI
spec, structured message types (text, interactive, templates, Flows), and
well-documented webhooks. The integration is an afternoon of plumbing, not a research
project.

### Ecosystem clients (surveyed 2026-10-21, hex.pm)

| Library | State | Assessment |
|---|---|---|
| `whatsapp_sdk` | Comprehensive: 79 service modules, 352 typed structs, generated from Meta's official OpenAPI spec | Best reference for our own generator; adoption/maintenance to spot-check before depending |
| `anu` (v0.2.1) | Fresh and idiomatic: requires Elixir 1.19+/OTP 27+, no hidden processes, explicit `Anu.Client` per phone number, Finch-based | Matches our style closely; candidate dependency if we don't generate our own |
| `whatsapp_elixir` (0.1.9) | Tiny adoption (single-digit downloads/30d) | Excluded |
| `whatsapp_cloud_api_wrapper` | 2 versions, minimal | Excluded |

Meta publishes **no first-party Elixir SDK** — all of the above are community work.

**Plan:** generate a thin client from Meta's spec (the `whatsapp_sdk` approach proves
this is tractable), keeping the surface we actually use: webhook verification, inbound
messages, outbound free-form + template messages, interactive buttons, Flows (ADR-0007),
media. `anu`/`whatsapp_sdk` serve as references. If generation drags, adopting `anu` is
the pre-approved fallback. A **Livebook test harness** exercises the real API (verify
token, sandbox number, template sends) as living documentation.

### Ingestion design (first-class, not an afterthought)

- One webhook endpoint; `X-Hub-Signature-256` verification; fast 200-ack, real work in
  Oban jobs.
- **Idempotency on Meta's message/WA-ID** — Meta redelivers webhooks; duplicate delivery
  must be a no-op.
- Outbound via Oban queues (per-tenant rate awareness later).
- Long-lived system-user token; secrets in runtime config, never in the repo.

### Cost facts (verified 2026-10)

- Per-message pricing since **2025-07-01**: charged per *delivered* message by category
  (marketing / utility / authentication / service) and destination market.
- **Utility templates delivered inside the open 24-hour customer-service window are
  free**; `service` category (free-form replies in the window) has its own rate;
  pricing updated again **2026-10-01** — rates table lives behind the pricing ADR
  link, and usage-based tenant billing is a line item in ADR-0006.

### Meta-side requirements (operational, not architectural)

Meta Business account + business verification, app setup, permanent system-user token,
phone number hosting, template approval workflow, and — for Flows — verified business
status (see ADR-0007).

## Consequences

- One fewer data processor (no BSP sees tenant messages) — directly serves the privacy
  criterion.
- We own the client surface: upgrades are a regen + diff, not someone else's roadmap.
- Meta's spec changes can break us faster than a maintained SDK would — accepted; the
  Livebook harness catches drift immediately.
- Message costs become a real COGS line; metering is designed in from day one
  (per-message delivery records).
